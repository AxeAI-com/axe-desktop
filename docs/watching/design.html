Watching, designed end to end

A watch checks one thing on a schedule and stays quiet until something is wrong. This book has every screen and state for every starter, in Paper and in dark, with the final copy and what each part does. The architecture and the owner's decisions follow the screens. Nothing here is built yet.

Five decisions that keep it small
  1. 01A starter fills in what kind of watch it is.Clicking one puts a chip in the composer, and you type only the address. Free text goes to your model once, and Axe never guesses the kind from keywords.
  2. 02Setting up a watch has one button.The plan shows two dropdowns (how often, when to tell you) and Start watching. A threshold comes from the site's own history, and you can change it in a reply.
  3. 03A quiet watch says nothing.No "All fine", no run counts. Quiet runs fold into one strip of ticks. Only an orange problem or a blue unread change asks for attention.
  4. 04Editing is four fields with no Save button.Target, how often, when to tell you, model. Each one saves as you change it. Pause, rename and delete live in the title's chevron menu.
  5. 05No extra surfaces.No Today strip, no "While you're away" cards, no summary watch to set up. The sidebar lists only watches with a problem. The morning summary comes built in and appears only when there's news.
  6. 06One composer, the chat’s own.Same + menu, @ and / menus, mic and model picker everywhere. Watching adds a kind chip, a Watch section in +, Watches in @ and four / commands, and changes nothing else.

How a sentence becomes a watch

    
    
      
  1. A starter sets kind explicitly. The composer only asks for the target, and the sentence in the bubble is written from a template, for example "Tell me if {site} goes down or gets slow."
    2. 
      
  2. Free text goes once to the model picked in the composer, with structured output: { kind, target, every?, notify?, condition? }, where kind is one of the six or unclear. Axe models use their JSON mode. CLI agents get a one-shot prompt in plan mode with a JSON-only reply that is validated against the schema. Local models use their JSON format option.
    3. 
      
  3. The deterministic fallback runs when there is no model or the reply doesn't validate. It extracts the first URL or domain with the same parser the chat already uses. If it finds one, Axe asks "What should I watch on {target}?" and offers the five starters. If not, it asks "What should I watch?" It never maps words to a kind.
    4. 
      
  4. A missing target becomes the question "Which site?" (or page, product page, domain, repo), asked inline with the kind already set.
    5. 
      
  5. Validation runs the kind's plain check once before the plan appears. It catches a domain that doesn't exist, a 404, a page that needs a sign-in, no price, or a repo Axe can't see. The plan shows real numbers from that check ("It's $48 and in stock"). That check is also the first run, so it isn't repeated after Start.
    6. 
    


    
The run pipeline

    

    
    
      
  • Compare with the previous run. Each check returns findings with a stable key (down, slow:/, dmarc:none, alert:GHSA-…, page:hash). A key that isn't open yet opens a finding and notifies once. A key that's already open stays quiet. A finding resolves after one clean run for uptime and two for the rest. If it comes back later, it's a new finding.
    • 
      
  • Run status is quiet, news, problem or failed. A failed run means Axe couldn't check (offline, timeout, model missing), so it is never shown as a problem the first time. Three failed runs in a row become a "Couldn't reach" problem. When the Mac is offline, nothing runs and nothing fails.
    • 
      
  • The notify rule applies to new findings and news only. It doesn't apply to snoozed or expected findings, to the first run, to the watch you are looking at, or when the watch is set to "In the morning summary". "Back to normal" is sent only for a problem that notified and then cleared by itself.
    • 
      
  • Thresholds come from history. Usual is the 7-day median, and slow means above 2× usual and over 2 s. A reply like "tell me above 3 s" sets a fixed one. "That's expected" adds the finding's key to expected, or for slow it raises usual to the current value.
    • 
      
  • The morning summary is plain text from a template, with no model. It covers findings opened or cleared since the last summary, unread news, and watches that couldn't run. It is shown at 8:00 (Settings, Notifications) and only if that list isn't empty.
    • 
    


    
Scheduling

    
Real today: watches run on this Mac, while it is awake and Axe is open. Cloud runs are not real: runs/cloud.ts gets a 403 because axeai.com accepts cloud agents only from browser sign-ins. This design leaves the cloud out.

    
    
      
  • One scheduler in the main process ticks every 30 s and runs due watches, three at a time, with up to 10% jitter so they don't all start together.
    • 
      
  • After sleep (powerMonitor resume), each overdue watch runs once. Missed times are skipped, never replayed.
    • 
      
  • Closing the window keeps Axe running, as Mac apps do. The first watch turns on Open at login (decision 1) so watches survive a restart.
    • 
      
  • The existing power keeper stays, set to "while something runs", so a run that starts can finish. It can't wake a sleeping Mac. Watches don't claim "24/7".
    • 
      
  • Later, if axeai.com runs plain checks server-side, uptime, page, price and security could run there too. Repo folders and local models never can.
    • 
    


    
The fix handoff

    
    
      
  1. A finding carries fix: "agent" | "record" | "none". Speed, headers and repo alerts are agent fixes. DNS records are record fixes. Page and price changes have no fix.
    2. 
      
  2. Agent: "Fix with Claude Code" (the CLI the user has, else Do it with their Axe model) starts a turn in the watch's own thread. On the first fix, Axe asks which folder holds the code and remembers it on the watch. The brief is built from the evidence, not by a model: the problem, the numbers, the files, and "Make the smallest change that fixes this. Don't commit or deploy." It starts in plan mode, so the existing plan card (Start) and changes panel (Keep all, Undo all) appear.
    3. 
      
  3. Re-verify: repo fixes re-run the folder checks right away. Site fixes need a deploy, so the thread says so and offers Check now. The finding moves to fixed only when a run shows it is gone. If it's still there, the thread says "Still {headline}" and offers Try again.
    4. 
      
  4. Record: Copy record, then Check now. DNS can take a while, so the next scheduled run also checks.
    5. 
    


    
One composer

    
    
      
  • Watching renders the chat's Composer, never its own box. The page uses <Composer variant="start" surface="watching" /> (docked once there are watches) and a watch uses <Composer variant="docked" threadId={watch.threadId} />. Both get the + menu, @ and / menus, paste and drop, the mic with DictationStrip, and ModelPicker in the toolbar under the box.
    • 
      
  • surface="watching" changes four things only. The placeholder. A kind chip slot in the text row. Send calls watching:draft with the picked answerer instead of starting a chat turn. The menus add Watching items.
    • 
      
  • The + menu gets a Watch section with the five starters, on both surfaces. In chat, picking one opens Watching with that chip.
    • 
      
  • lib/mentions gets a watch kind, listed from watching:list. On the Watching page a message naming one watch is routed to that watch's thread. In a chat, a watch reference attaches { name, kind, target, latest, open findings } as context, the same way a file is attached.
    • 
      
  • The / menu gets a Watching group: /check, /pause, /resume, /summary. A fix turn is an agent turn, so it also shows the agent's commands, folder chip, mode menu and context ring.
    • 
      
  • The model picked on the page is the default for the next watch. Each watch stores its own answerer, which Edit changes. The picker never shows prices or plans.
    •

The renderer never runs a check or opens a network connection. The main process owns the store, the scheduler and the checks. Checks get injected deps (fetch, dns, tls, net, exec, clock) so tests run offline. The mock bridge serves every screen in this book by id: ?mock=watching&screen=<id>.
